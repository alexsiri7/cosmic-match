## 1. Current Security Posture (V1)

Cosmic Match V1 has no backend of its own and gameplay works offline, but the app does
make outbound HTTPS requests to the third-party endpoints listed below. Cleartext HTTP is
blocked by `network_security_config.xml` (§4.2), and `FeedbackService` sends nothing when
`FEEDBACK_WORKER_URL` is not an `https` URL.

| Aspect | Status |
|---|---|
| Network access | HTTPS only, to the endpoints in the table below |
| INTERNET permission | Declared in the main `AndroidManifest.xml` (all build types) for those endpoints; the debug and profile manifests also declare it for Flutter tooling |
| Data storage | Local-only via Hive; progress and the offline feedback queue are AES-256 encrypted when a Keystore key is available (§1.2) and HMAC-SHA256 signed (§1.1) |
| Authentication | None |
| Permissions requested | None beyond default |

**Network endpoints:**

| Endpoint | When | What is sent | Retention |
|---|---|---|---|
| Sentry (`SENTRY_DSN`) | Only in builds compiled with a `SENTRY_DSN` value (release CI on push; see below) | Crash reports and app-start/stop session events | 90 days at Sentry |
| Feedback worker (`FEEDBACK_WORKER_URL`, default `https://feedback.alexsiri7.workers.dev/`; `lib/services/feedback_service.dart`) | When the user submits in-app feedback with the consent box ticked, and when connectivity returns while the offline queue holds items. Not gated on `SENTRY_DSN`: every build has a worker URL | Feedback type, description, annotated screenshot, app version, OS and device model; signed with `FEEDBACK_HMAC_SECRET` when one was compiled in (§6.3) | The Cloudflare Worker files it as a public GitHub issue on `alexsiri7/cosmic-match`, kept until deleted. Undelivered items stay in the encrypted local queue for at most 7 days (`kFeedbackQueueTtlDays`) |
| Google Fonts CDN (`google_fonts`; `lib/widgets/stat_card.dart`, `lib/screens/feedback_sheet.dart`) | The first time IBM Plex Mono is rendered; the font is not bundled as an asset, and is cached on device after download | A plain font-file request (IP address and user agent); no app data | Governed by Google's privacy policy |
| Google Play (`in_app_update`; `lib/services/in_app_update_service.dart`) | On Android, a Play Core update check after the first frame; a flexible update is downloaded by the Play Store if one is available | The request is made by Google Play services on the app's behalf; no app data | Governed by Google's privacy policy |

These match the disclosures in `docs/privacy.html`.

**Crash reporting**: When built with a `SENTRY_DSN` compile-time value (release CI
only), the app sends pseudonymous crash reports and app-start/stop session events
(Sentry auto session tracking, left at its default `enableAutoSessionTracking = true`)
to Sentry over HTTPS. Events carry a stack trace, app version, device model, OS version
and a random per-install identifier generated by the Sentry SDK (used as the event's
user id so Sentry can count affected installs). `sendDefaultPii` is `false` (no IP
address, name, email or account), and no game state or screenshots are included. This
matches the disclosure in `docs/privacy.html`. Local and debug builds with no DSN
configured send nothing to Sentry.

### 1.1 Client-Side Integrity Controls (SEC-008)

Six mitigations make trivial client-side manipulation harder.
They do not stop a determined attacker on a rooted device, but raise the effort bar and
will become more meaningful when leaderboards are added (see §2).

| Control | Implementation | Limit |
|---------|---------------|-------|
| FSM Input Gate | `GridTile.onTapDown` and `GridTile.onDragStart` drop all taps and swipes when `game.phase != idle`; `Match3Game.onTileTap` and `Match3Game.onTileSwipe` re-check the phase themselves | Prevents input injection during animations |
| Score Clamp | `Score.add()` ignores non-positive inputs and clamps to 999,999,999 | Prevents integer overflow exploits |
| Cascade Depth Limit | `CascadeController.maxDepth = 20`; `increment()` is a no-op once cap is reached | Prevents infinite cascade loops from bugs in gravity/refill logic |
| HMAC-SHA256 Save Integrity | `LevelProgress.toMap()` and `PendingFeedback.toMap()` store an HMAC-SHA256 over canonicalized (key-sorted) fields, keyed with a device-local key from `KeyService` (`lib/core/crc_integrity.dart`); `ProgressService._isValid()` resets tampered progress to `LevelProgress.initial()` and `FeedbackService._isValid()` drops tampered queue entries. Without a key, saves are skipped and loads treat data as invalid | Prevents forging save data off-device; the key lives in the Android Keystore, so it does not stop an attacker with root on the device. Replaced a forgeable CRC32 in #201 |
| Save Semantic Validation | `LevelProgress.fromMap()` rejects `starsEarned` outside 0–3 and `bestScore` outside 0–999,999,999; `ProgressService.load()` rejects a record whose `level` differs from the level it was stored under. Either resets that level to `LevelProgress.initial()` | Stops an attacker holding the HMAC key from signing impossible values or replaying one level's record under another; values inside the valid ranges are still accepted |
| Feedback Rate Limit | `RateLimitService`, checked by `FeedbackService.submit()` and `flushQueue()` | 30 s cooldown and 5 submissions per hour per device (SEC-RPT-008); fails open on a storage error |

**Note**: If leaderboards are added (post-V1), SEC-008 risk level rises to MEDIUM. Server-side score validation will be required at that point — see §2.

### 1.2 Hive Encryption at Rest (SEC-004)

Keystore via `flutter_secure_storage`. `main()` passes the resulting `HiveAesCipher` to both
`ProgressService` and `FeedbackService`, which pass it to `Hive.openBox()`, rendering the
on-disk boxes opaque ciphertext. If the Keystore is unavailable (emulator, broken hardware,
a transient failure), `getCipher()` returns `null` and the services never open their boxes:
nothing is saved or loaded for that session (#317). Opening the encrypted box without its
cipher would make Hive's crash recovery truncate it, and writing would store records in
plaintext.

## 3. Authentication

### 3.1 Provider Comparison

| Criteria | Firebase Auth | Supabase Auth |
|---|---|---|
| Flutter SDK maturity | Mature, first-party | Actively maintained by Supabase; slightly less Flutter-ecosystem integration than Firebase |
| Social auth (Google, Apple) | Built-in | Built-in |
| Self-hosting | No | Yes (Docker) |
| Vendor lock-in | High (Google ecosystem) | Low (open source, PostgreSQL) |
| Pricing at scale | Pay-as-you-go, can spike | Predictable tiers, free self-hosted |
| Data sovereignty | Google-managed regions | Full control if self-hosted |
| Offline support | Good (cached credentials) | Limited |

### 3.2 Decision Criteria

Choose **Firebase Auth** if:
- You want the fastest integration path with Flutter
- Google ecosystem services (Analytics, Crashlytics) are also planned
- Offline credential caching is important

Choose **Supabase Auth** if:
- Data sovereignty or self-hosting is a requirement
- You want to avoid vendor lock-in
- The backend will use PostgreSQL (Supabase provides a full Postgres database)

### 3.3 Requirements (Either Provider)

- Support social sign-in (Google) — strongly recommended to reduce sign-up friction; Apple Sign-In is required on iOS (App Store rule) if any other social provider is offered
- Implement account deletion — required for Play Store compliance (apps with account creation must offer deletion)
- Support anonymous/guest accounts for players who do not want to sign in
- Store auth tokens securely using `flutter_secure_storage`, never in plain Hive boxes
- Implement token refresh logic with exponential backoff
- Add a sign-out flow that clears local credentials

## 4. Android Network Security

### 4.1 Background

Android 9+ (API 28+) blocks cleartext HTTP by default. Since `minSdk = 26` (Android 8), the app spans both behaviours. A `network_security_config.xml` must be created when any network calls are added.

### 4.2 Network Security Config

`android/app/src/main/res/xml/network_security_config.xml` is in place and blocks all
cleartext traffic. It is referenced in `android/app/src/main/AndroidManifest.xml` via
`android:networkSecurityConfig`. When backend API calls are added, extend the config
with certificate pinning (template below):

```xml
<?xml version="1.0" encoding="utf-8"?>
<network-security-config>
    <!-- Block all cleartext (HTTP) traffic in production -->
    <base-config cleartextTrafficPermitted="false">
        <trust-anchors>
            <certificates src="system" />
        </trust-anchors>
    </base-config>

    <!-- Optional: pin certificates for your API domain -->
    <!--
    <domain-config>
        <domain includeSubdomains="true">api.cosmicmatch.com</domain>
        <!-- Set expiration at least 2 years from today. Schedule a calendar reminder
             to rotate pins and update this date before it expires. -->
        <pin-set expiration="2028-04-01">
            <pin digest="SHA-256">YOUR_PIN_HASH_HERE</pin>
            <pin digest="SHA-256">YOUR_BACKUP_PIN_HASH_HERE</pin>
        </pin-set>
    </domain-config>
    -->
</network-security-config>
```

Reference it in `android/app/src/main/AndroidManifest.xml`:

```xml
<application
    android:networkSecurityConfig="@xml/network_security_config"
    ...>
```

### 4.3 Certificate Pinning

Certificate pinning is recommended for production API endpoints. Always include a backup pin. Set an expiration date and rotate pins before expiry.

## 5. API Security

### 5.1 Rate Limiting

| Endpoint Type | Recommended Limit |
|---|---|
| Auth (login/register) | 5 requests per minute per IP |
| Leaderboard submit | 10 requests per minute per user |
| Leaderboard read | 30 requests per minute per user |
| Daily challenge fetch | 5 requests per minute per user |

Implement rate limiting server-side. Firebase provides App Check for abuse prevention. Supabase supports rate limiting via PostgreSQL policies or a reverse proxy (e.g., Nginx, Cloudflare).

### 5.2 CORS Configuration

If the backend exposes a REST API that may be called from a web client:

```
Access-Control-Allow-Origin: https://cosmicmatch.com
Access-Control-Allow-Methods: GET, POST
Access-Control-Allow-Headers: Authorization, Content-Type
Access-Control-Max-Age: 86400
```

Do **not** use `Access-Control-Allow-Origin: *` in production.

### 5.3 Security Headers

All backend HTTP responses must include:

| Header | Value | Purpose |
|---|---|---|
| `Strict-Transport-Security` | `max-age=63072000; includeSubDomains; preload` | Enforce HTTPS |
| `Content-Security-Policy` | `default-src 'self'` | Prevent XSS |
| `X-Content-Type-Options` | `nosniff` | Prevent MIME sniffing |
| `X-Frame-Options` | `DENY` | Prevent clickjacking |
| `Referrer-Policy` | `strict-origin-when-cross-origin` | Limit referrer leakage |

## 6. Secrets Management

### 6.1 Rules

- **Never** hardcode API keys, secrets, or credentials in source code
- **Never** commit `.env` files, keystores, or `key.properties` to the repository
- Use environment variables or a secrets manager for all sensitive values

### 6.2 `.gitignore` Coverage

The repository `.gitignore` already excludes:

```
*.jks
*.keystore
key.properties
.env
.env.*
*.env
```

When adding a backend, verify these entries remain in place.

### 6.3 Environment Variable Pattern

Create a `.env.example` (committed) documenting required variables without real values:

```
# Backend API
API_BASE_URL=https://api.cosmicmatch.com
API_KEY=YOUR_API_KEY_HERE

# Firebase (if used)
FIREBASE_PROJECT_ID=YOUR_PROJECT_ID_HERE
FIREBASE_API_KEY=YOUR_FIREBASE_API_KEY_HERE

# Supabase (if used)
SUPABASE_URL=YOUR_SUPABASE_URL_HERE
SUPABASE_ANON_KEY=YOUR_SUPABASE_ANON_KEY_HERE
```

Use `--dart-define` or `--dart-define-from-file` to inject values at build time:

```bash
flutter build apk \
  --dart-define=API_KEY=... \
  --dart-define=API_BASE_URL=...
```

Or with a file (Flutter 3.17+):
```bash
flutter build apk --dart-define-from-file=.env
```

Values passed via `--dart-define` are compiled into the binary as string literals. They are not bundled as asset files, but they are **not confidential**: anyone with the APK can recover them by static analysis, and `--obfuscate` does not hide string literals. Treat every dart-define value as public — including `FEEDBACK_HMAC_SECRET`, which is shared by every install and only raises the bar for casual abuse of the feedback worker; it is not client authentication. Never commit actual `.env` files to the repository.

> ⚠️ Do **not** use `flutter_dotenv` in release builds — it bundles the `.env` file into the APK's assets directory, where it can be extracted from a downloaded APK.

## 7. Flutter Integration Patterns

### 7.1 Repository Pattern

Follow the existing `ProgressRepository` pattern when adding backend repositories. New classes should use constructor injection and clear method signatures with doc comments:

```dart
/// Repository for authenticating users and managing sessions.
class AuthRepository {
  final AuthClient _client;

  AuthRepository({required AuthClient client}) : _client = client;

  /// Sign in with Google and return the user profile.
  Future<UserProfile> signInWithGoogle() async {
    // ...
  }

  /// Sign out and clear local credentials.
  Future<void> signOut() async {
    // ...
  }
}
```

### 7.2 Initialisation Pattern

Follow `main.dart`'s async initialisation pattern. Initialise auth and network clients before `runApp()`:

```dart
Future<void> main() async {
  WidgetsFlutterBinding.ensureInitialized();

  // Existing Hive init...
  await Hive.initFlutter();

  // New: initialise auth client
  final authClient = await AuthClient.initialize();
  authRepository = AuthRepository(client: authClient);

  // New: initialise API client
  apiRepository = ApiRepository(baseUrl: Environment.apiBaseUrl);

  runApp(const CosmicMatchApp());
}
```

## 8. Code Signing

### 8.1 Current State

Release signing is implemented via `android/app/build.gradle.kts`. When
`android/key.properties` is present, the release build uses the configured keystore.
When absent (local dev without a keystore), the release build falls back to debug signing.

See `android/key.properties.example` for the required file format, and §8.2 for keystore
generation instructions.

### 8.2 Production Signing Requirements

Before publishing to the Play Store:

1. Generate a production keystore: `keytool -genkey -v -keystore cosmic-match-release.jks -keyalg RSA -keysize 2048 -validity 10000 -alias cosmic-match`
2. Store the keystore **outside** the repository (never commit it)
3. Create `android/key.properties` (gitignored) with:
   ```
   storePassword=YOUR_STORE_PASSWORD_HERE
   keyPassword=YOUR_KEY_PASSWORD_HERE
   keyAlias=cosmic-match
   storeFile=/path/to/cosmic-match-release.jks
   ```
4. Reference `key.properties` in `build.gradle.kts` for the release signing config
5. For CI/CD, store the keystore as a Base64-encoded GitHub Secret and decode it during the build step

### 8.3 Play App Signing

Enrol in Google Play App Signing. This lets Google manage the app signing key while you use an upload key — reducing the risk of a lost keystore locking you out of updates.

### 8.4 `build.gradle.kts` Signing Config (Kotlin DSL)

The implemented config reads from `key.properties` only. The CI writes `key.properties`
from secrets before running `flutter build` — **do not** add `System.getenv()` reads in
Gradle, as those values can be captured in Gradle's configuration cache.

```kotlin
// android/app/build.gradle.kts
import java.util.Properties
import java.io.FileInputStream

val keyPropertiesFile = rootProject.file("key.properties")
val keyProperties = Properties()
if (keyPropertiesFile.exists()) {
    keyProperties.load(FileInputStream(keyPropertiesFile))
}

android {
    signingConfigs {
        create("release") {
            // Properties only set when key.properties exists.
            // buildTypes.release falls back to debug signing when this block is empty.
            if (keyPropertiesFile.exists()) {
                keyAlias = keyProperties.getProperty("keyAlias")
                    ?: error("keyAlias missing from android/key.properties — see key.properties.example")
                keyPassword = keyProperties.getProperty("keyPassword")
                    ?: error("keyPassword missing from android/key.properties")
                storeFile = file(keyProperties.getProperty("storeFile")
                    ?: error("storeFile missing from android/key.properties"))
                storePassword = keyProperties.getProperty("storePassword")
                    ?: error("storePassword missing from android/key.properties")
            }
        }
    }
    buildTypes {
        release {
            signingConfig = if (keyPropertiesFile.exists())
                signingConfigs.getByName("release")
            else
                signingConfigs.getByName("debug")
        }
    }
}
```

> ⚠️ Do **not** check in `key.properties` — it is gitignored. Copy `android/key.properties.example` and fill in real values for local builds.

### 8.5 GitHub Actions CI/CD Signing Snippet

The release job in `.github/workflows/ci.yml` implements signing in its "Resolve signing
keystore" step. Secrets reach the step only through its `env:` block; no `${{ secrets.* }}`
expression is interpolated into `run:` script text, so a secret value can never be parsed
as shell. `pull_request` runs receive empty values and always sign with a throwaway
keystore, so PR-controlled build code never sees release secrets (SEC-01).

```yaml
# .github/workflows/ci.yml (release job — signing, abridged)
- name: Resolve signing keystore
  env:
    KEYSTORE_B64:   ${{ github.event_name != 'pull_request' && secrets.KEYSTORE_BASE64 || '' }}
    STORE_PASSWORD: ${{ github.event_name != 'pull_request' && secrets.KEYSTORE_STORE_PASSWORD || '' }}
    KEY_PASSWORD:   ${{ github.event_name != 'pull_request' && secrets.KEYSTORE_KEY_PASSWORD || '' }}
    KEY_ALIAS:      ${{ github.event_name != 'pull_request' && secrets.KEYSTORE_KEY_ALIAS || '' }}
  run: |
    # Decode KEYSTORE_B64; validate it with
    #   keytool -list -storepass "${STORE_PASSWORD:-}" ...
    # and fall back to a throwaway keystore if absent or unreadable.
    {
      echo "storePassword=$STORE_PASSWORD"
      echo "keyPassword=$KEY_PASSWORD"
      echo "keyAlias=$KEY_ALIAS"
      echo "storeFile=${{ github.workspace }}/$KS"
    } > android/key.properties

- name: Clean up signing credentials
  if: always()
  run: rm -f android/cosmic-match-release.jks android/key.properties
```

> **Known exception**: the keystore validation passes the store password to `keytool` as a
> `-storepass` argument, so it is on that process's command line for the duration of the
> call. It is visible only to processes on the same ephemeral GitHub-hosted runner, and
> GitHub masks secret values in logs. Every other use keeps secrets out of argv.

**Required GitHub Secrets:**

| Secret | Value |
|--------|-------|
| `KEYSTORE_BASE64` | **Linux:** `base64 -w 0 cosmic-match-release.jks` <br> **macOS:** `base64 cosmic-match-release.jks \| tr -d '\n'` |
| `KEYSTORE_STORE_PASSWORD` | Store password |
| `KEYSTORE_KEY_ALIAS` | `cosmic-match` |
| `KEYSTORE_KEY_PASSWORD` | Key password |

`PLAY_SERVICE_ACCOUNT_JSON` belongs in the Play **environments**, not the repository secrets — see §8.7 (until that setup is done, the repository-level copy is still used).

### 8.6 Key Properties Example File

A committed example file at `android/key.properties.example` documents the expected properties schema. Copy it to `android/key.properties` and fill in real values. The real `key.properties` is gitignored.

### 8.7 Play Publishing Environments (SEC-07)

Play uploads run only in jobs bound to a GitHub Environment, so the Play service account is readable
only there and production releases wait for a reviewer (#310). The `release` job builds and signs on
every PR, `main` push and tag, takes no environment, and hands the signed AAB, APK and R8 mapping to
the publish jobs as same-run artifacts.

| Environment | Job(s) | Protection | Secrets |
|-------------|--------|------------|---------|
| `production` | `ci.yml` → `publish-production` (`v*` tags) | Required reviewer; deployment tags `v*` only | `PLAY_SERVICE_ACCOUNT_JSON` |
| `play-internal` | `ci.yml` → `publish-internal` (`main` pushes); `setup-store-listing.yml` → `upload-listing` | Deployment branch `main` only; no reviewers | `PLAY_SERVICE_ACCOUNT_JSON` |

`.github/workflow-tests/test_ci_release_gate.py` fails if a job in any workflow reading the Play
secret has no environment, if `release` gains one, or if `contents: write` moves out of
`publish-production`.

GitHub creates a referenced environment unprotected and falls back to the repository secret, so the
gate is only active once a maintainer completes this one-time setup, in order:

1. Settings → Environments → `production`: add the maintainer as a required reviewer; set deployment
   branches and tags to "Selected" with the tag rule `v*`. Enable "Prevent self-review" if there is a
   second maintainer.
2. Settings → Environments → `play-internal`: set deployment branches to "Selected" with branch `main`.
   No reviewers.
3. Add the environment secret `PLAY_SERVICE_ACCOUNT_JSON` to both environments. Prefer a separate
   service account for `play-internal` holding only the Play Console testing-track and store-listing
   permissions, keeping production-release permission on the `production` account.
4. Push to `main` and confirm `Publish (internal track)` runs unattended.
5. Delete the repository-level `PLAY_SERVICE_ACCOUNT_JSON` secret.
6. Settings → Rules → add a tag ruleset targeting `v*` that restricts creation, update and deletion to
   the maintainer and blocks force-push.
7. On the next `v*` tag, confirm `Publish (production)` waits for review before uploading, cutting the
   GitHub Release and notifying.

Production releases ship at 100% (`status: completed`) after approval; staged rollout is not used.

## 9. Data Privacy

### 9.1 Current State (V1)

- All game data is stored locally on-device via Hive
- Every outbound endpoint, what it receives and how long it is kept is listed in §1
- Release builds with a `SENTRY_DSN` value send pseudonymous crash reports
  and app-start/stop session events to Sentry over HTTPS (stack traces, app
  version, device/OS metadata, and a random per-install identifier generated
  by the Sentry SDK); `sendDefaultPii` and `attachScreenshot` are both
  `false`, so no IP address, account or contact details, or screenshots are
  included. Sentry retains this data for 90 days (see `docs/privacy.html`)
- Builds without a DSN send nothing to Sentry, but still reach the feedback
  worker, Google Fonts and Google Play as described in §1
- In-app feedback (sent only after the user ticks the consent box) carries the
  description, annotated screenshot, app version, OS and device model, and is
  published as a public GitHub issue
- No personal information is collected beyond the pseudonymous Sentry
  per-install identifier above and anything a user chooses to include in
  feedback

### 9.2 When a Backend Is Added

- Create a Privacy Policy (required for Play Store)
- Implement data export (GDPR right of access)
- Implement account deletion (GDPR right to erasure, Play Store requirement)
- Log only what is necessary — no PII in server logs
- Encrypt data in transit (TLS 1.2+) and at rest

## 11. Dependency Pinning and Audit Strategy

### 11.1 Current State (V1)

All direct dependencies use caret (`^`) constraints in `pubspec.yaml`, allowing patch and compatible minor updates while preventing accidental major-version breakage. `pubspec.lock` is committed to version control, pinning all transitive dependencies to known-good versions.

| Control | Implementation | Purpose |
|---------|---------------|---------|
| Lockfile commit | `pubspec.lock` tracked in git | Deterministic builds across machines and CI |
| Lockfile enforcement | `flutter pub get --enforce-lockfile` as the first flutter command in every CI job (guarded by `.github/workflow-tests/test_lockfile_enforced.py`) | A stale or hand-edited `pubspec.lock` fails CI instead of resolving different transitive versions (#319) |
| Caret constraints | `^` prefix on all direct deps | Allow security patches; block breaking changes |
| Gradle wrapper checksum | `distributionSha256Sum` in `android/gradle/wrapper/gradle-wrapper.properties` | Wrapper refuses a distribution ZIP whose SHA-256 differs from the official hash for the pinned `distributionUrl`; update both together on a Gradle bump |
| Automated CVE monitoring | `.github/dependabot.yml` (weekly; `pub`, `github-actions`, `pip` for `store-listing/`, `gradle` for `android/`) | Dependabot opens PRs when vulnerabilities found |

**Note**: `pubspec.lock` must be updated and recommitted whenever a dependency is added, removed, or upgraded. Never run `flutter pub upgrade` without reviewing the resulting lock diff.

### 11.2 Constraints

- **Limited network surface**: V1 has no backend of its own; its network code is limited to the endpoints in §1 (Sentry, the feedback worker, Google Fonts, Google Play). A compromised dependency could reach the network through the `INTERNET` permission, but there are no user accounts or credentials on the device to exfiltrate. Risk level: LOW.
- **CI**: `.github/workflows/ci.yml` runs `flutter analyze`, `flutter test` and the release build on every pull request and on pushes to `main` and release tags, and `.github/workflows/unsafe-change.yml` gates factory-screened PRs against the denylist in `.github/unsafe-change.yml`. Every job runs `flutter pub get --enforce-lockfile` before any other flutter command, so a stale or hand-edited lockfile fails CI instead of resolving different transitive versions.

### 11.3 Quarterly Transitive Dependency Review

Every quarter, perform the following manually:

1. Run `dart pub outdated` to identify outdated direct and transitive dependencies
2. Review open Dependabot security alerts for the repository (the Dart toolchain has no built-in vulnerability-audit command; Dependabot checks `pubspec.lock` against the GitHub Advisory Database)
3. Review Dependabot PRs — merge security patches promptly; schedule major upgrades
4. Update `pubspec.lock` by running `flutter pub upgrade --major-versions` for intentional major bumps only, reviewing the diff before committing

### 11.4 When a Backend Is Added
